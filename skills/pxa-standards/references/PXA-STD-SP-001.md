## 規範語法

本文件採用 ANSI/NISO Z39.18 與 DoD/NASA 技術標準規範語法：

| 關鍵字 | 英文原文 | 意義 | 約束力 |
|--------|---------|------|--------|
| **必須** | shall | 強制要求，無例外 | 強制 |
| **禁止** | shall not | 絕對禁止 | 強制 |
| **建議** | should | 強烈建議，除非有文件化正當理由 | 建議 |
| **不建議** | should not | 不建議，除非有文件化正當理由 | 建議 |
| **可選** | may | 視情況選用 | 選用 |

**判定方式標註**：可由 `check_sp.py` 確定性判定之規則標 **[S]**（以腳本結果為準）；需人工審查之規則標 **[H]**。未標註者為定義性條文。

## 1. 範圍

### 1.1 目的

本標準定義本組織（PXA）所有技術報告的類別、編號、審查、發行管控與證據品質之治理規則，確保跨專案、跨作者的報告品質一致性。

本標準為「治理規則的單一真實來源」；報告之結構、模板與格式規則歸 PXA-STD-SP-002。

### 1.2 適用範圍

| 類別 | 適用文件 |
|------|---------|
| **SP（標準）** | 公司標準、技術指南、手冊、範本（`PXA-STD-SP` 系列） |
| **TR（技術報告）** | 研究、設計、測試報告；跨專案之單一議題深度研究或針對具體專案問題之報告皆屬之 |

本標準不適用於：提案文件、合約文件、內部備忘錄、會議紀錄。

## 2. 報告類別

### 2.1 類別

PXA 文件分兩類。原 SP（研究）、TM、TP 三類自 v4.0 起合併為技術報告（裁定 #12）。

| 類別 | 系列 | 全稱 | 定義 | STRN 格式 | 審查等級 |
|:----:|:----:|------|------|-----------|----------|
| **SP（標準）** | `PXA-STD-SP` | Special Publication | 公司標準、技術指南、手冊、範本 | `PXA-STD-SP-{NNN}` | 核准權責主管核准 |
| **TR（技術報告）** | `PXA-{CODE}-TR` | Technical Report | 研究、設計、測試之技術報告；涵蓋跨專案之單一議題深度研究與針對具體專案問題之單主題報告 | `PXA-{CODE}-TR-{YYYY}-{NNN}` | 同儕審查 |

所有技術報告共用同一份內文骨架（TP 骨架）、同一份前頁與同一份 Word 範本（SP-002）。

### 2.2 類別判定與報告性質

| # | 判定條件 | 類別 |
|:-:|---------|:----:|
| 1 | 公司級規範、標準、範本、手冊 | SP（標準） |
| 2 | 其餘技術文件：研究、分析、設計、建模、測試、驗證 | TR |

技術報告不再細分類型。每份報告 **必須** 宣告**報告性質**（研究／設計／測試，可並列），其定義、判斷問句與各性質之必要章節見 SP-002 §3.1。報告性質只決定章節之裁剪，不影響編號與審查等級。

### 2.3 報告間之引用

報告之間無階層關係，平等引用；原「vault → SP → TM／TP」單向信任鏈取消（裁定 #12）。

| 規則 | 說明 | 判定 |
|------|------|:----:|
| 獨立性 | 每份報告 **必須** 可獨立閱讀、獨立審核、獨立發行 | [H] |
| 引用義務 | 核心工程假設或公式 **必須** 追溯至既有報告或外部文獻，不得無來源陳述 | [H] |
| 內部引用格式 | 引用 PXA 報告以 `[PXA-{STRN}, §X.Y]` 標示，文獻層級為 L1；**必須** 與外部文獻引用 `[Author Year]` 在形式上可區分（`PXA-` 前綴為區分標記） | [H] |
| 不重複推導 | 既有報告已建立之結論 **建議** 直接引用其 [C-n] 並確認適用條件相符，不重新推導；重新推導時說明理由 | [H] |
| 議題聚焦 | 每份報告 **建議** 聚焦於單一技術議題；整合多份報告之合成報告 **必須** 標註來源報告之編號與版本，由作者重新整合撰寫，**禁止** 直接拼接內容 | [H] |
| 結論可引用性 | 核心結論 **必須** 以 [C-n] 格式明確標示於結論章（SP-002 §3.5） | [S] |

### 2.4 產製與交付格式

報告以 Markdown 為單一真實來源（SSoT），結構依 PXA-STD-SP-002。**正式交付格式為 docx**：Report.md 通過合規 gate 後，以 scribe skill 之確定性轉換管線（pandoc＋Word 範本 `PXA-SP-template.dotx`＋`md2docx.py`）產出 `{STRN}.docx`——同一份 MD 永遠轉出同一版面；公式轉為 Word 原生方程式（OMML）、式號保留。PDF 需要時由 docx 另存。

| 規則 | 說明 | 判定 |
|------|------|:----:|
| MD 為 SSoT | 內容修訂 **必須** 回 MD 端修改後重轉，**禁止** 只改 docx | [H] |
| 轉換確定性 | docx **必須** 由轉換腳本產出，**禁止** 手工重排版面（版面調整改範本） | [H] |
| 人工編寫 | 不經 MD 而直接以 Word 範本人工編寫之報告，以該 docx 為正本，上列兩項不適用；結構、前頁與版面仍依 SP-002 與範本 | [H] |

紙本歸檔之 LaTeX 版由 latexer skill 自定稿 MD 轉出，非正式交付格式。

### 2.5 舊制報告之處置

| 情境 | 處置 |
|------|------|
| 已發行或已編號之 SP（研究）、TM、TP | 編號維持有效，不重編；引用時沿用原編號 |
| 舊制報告修訂 | 沿用原編號遞增版本；內文於該次修訂轉為現行骨架並宣告報告性質 |
| 新立案報告 | 一律以 TR 編號 |

## 3. 報告編號（STRN）

兩種格式均以 ANSI/NISO Z39.23 為基礎，裁剪為連字號分隔以相容檔案系統。

### 3.1 兩種格式

**SP（標準）**：

```
PXA-STD-SP-{NNN}
├── PXA-STD    固定前綴（PXA 標準系列）
└── SP-{NNN}   流水號三碼（001, 002, ...）
```

**TR（技術報告）**：

```
PXA-{CODE}-TR-{YYYY}-{NNN}
├── PXA      組織代碼（固定）
├── {CODE}   跨專案報告填技術領域代碼（TOPIC）；專案報告填專案代碼（PROJECT）（§3.2）
├── TR       類別（固定）
├── {YYYY}   4 位西元年
└── {NNN}    3 位流水號，同一 {CODE} 內年度歸零
```

舊制格式 `PXA-{TOPIC}-SP-{YYYY}-{NNN}`、`PXA-{PROJECT}-TM-…`、`PXA-{PROJECT}-TP-…` 僅存在於已編號之報告（§2.5），不再新發。

### 3.2 代碼（TOPIC 與 PROJECT）

| 種類 | 規則 | 範例 |
|------|------|------|
| TOPIC（技術領域） | 用於結論跨專案通用之報告；代碼由核准權責主管**核准**後方可新增 | `AERO` 氣動力學、`STRUCT` 結構、`GNC` 導引、導航與控制 |
| PROJECT（專案） | 用於針對具體專案之報告；2–6 字元大寫，定義於專案 Profile | `OSP` |

TOPIC 與 PROJECT 代碼 **禁止** 同名。

### 3.3 本地後綴（選用）

本地後綴以 `+` 分隔，附加於序號群之後。適用於技術報告；SP（標準）不使用。

| 後綴類型 | 格式 | 範例 |
|---------|------|------|
| 版本 | `+v{M}-{N}` | `+v1-0`、`+v2-1` |
| 設計階段 | `+{PHASE}{X}` | `+DP3`、`+SP2` |
| 狀態 | `+DRAFT`、`+REVIEW`、`+BASELINE` | `+DRAFT` |
| 修訂 | `+Rev{X}` | `+RevA` |
| 卷冊 | `+Vol{X}` | `+Vol2` |

多重後綴 **必須** 以 `+` 串接，順序為：版本 → 階段 → 狀態。

### 3.4 範例

| 報告編號 | 類別 | 說明 |
|---------|:----:|------|
| `PXA-STD-SP-001` | SP（標準） | PXA 技術報告治理標準 |
| `PXA-AERO-TR-2026-001` | TR | 氣動力學領域 2026 年第 1 份技術報告（跨專案） |
| `PXA-GNC-TR-2026-002+v1-0` | TR | GNC 領域第 2 份，版本 1.0 |
| `PXA-OSP-TR-2026-003+v1-0+DP3` | TR | Osprey 專案第 3 份，版本 1.0，設計階段 DP-3 |
| `PXA-OSP-TM-2026-001+v1-0` | 舊制 | 合併前已編號之報告，編號維持有效（§2.5） |

### 3.5 標示位置

報告編號 **必須** 出現於：封面、書名頁、每頁頁尾（或頁首）、DAA §I 文件識別欄；位置依 Word 範本。

### 3.6 編號登記表

每個代碼（TOPIC 或 PROJECT）**必須** 維護一份編號登記表，防止重號：

| 編號 | 標題 | 作者 | 日期 | 狀態 |
|------|------|------|------|------|
| `PXA-OSP-TR-2026-001` | 需求分析 | 張○○ | 2026-01-15 | 基線 |

### 3.7 版本規則

| 情境 | 版本變更 | 範例 |
|------|----------|------|
| 首版 | v1.0 | 初版發行 |
| 小幅修正（錯字、格式、數值微調） | 次版號 +1 | v1.0 → v1.1 |
| 重大變更（結構變更、設計點變更） | 主版號 +1，次版歸零 | v1.3 → v2.0 |

## 4. 審查與發行管控

### 4.1 審查等級

| 類別 | 最低審查等級 | 審查人 |
|:--------:|------------|--------|
| **SP（標準）** | 核准權責主管核准 | 核准權責主管 |
| **TR（技術報告）** | 同儕審查 | 至少一位**非作者**的合格技術人員 |

### 4.2 審查檢核項

技術審查 **必須** 至少涵蓋（參照 NASA SP–7602 Appendix B）：

| # | 檢核項 | 適用 |
|---|--------|------|
| 1 | 報告撰寫清晰，邏輯通順 | 全部 |
| 2 | 所有編號項（圖、表、公式、參考文獻、附錄）依序引用且編號正確 | 全部 |
| 3 | 無拼寫、文法、標點錯誤 | 全部 |
| 4 | 結論由正文資料支持 | 全部 |
| 5 | 引用文獻可識別且資訊充分 | 全部 |
| 6 | 圖表數據清晰一致 | 全部 |
| 7 | 符合資訊安全與出口管制要求 | 全部 |
| 8 | 完整公式推導可驗證 | 含推導者 |
| 9 | 敏感度分析覆蓋主要參數 | 含敏感度分析者 |
| 10 | 測試或驗證之方法與結果可追溯；測試項目有通過準則，偏差已記錄 | 測試性質 |

### 4.3 審查結果等級

| 等級 | 英文 | 判定條件 | 處置 |
|------|------|----------|------|
| **A** | Accept | 所有必須項通過，建議項無重大缺失 | 直接放行，進入 DAA 簽核 |
| **B** | Accept with Minor Correction | 必須項全數通過，但 ≤ 3 項建議/可選缺失或格式瑕疵 | 作者修正後免重審，審查者確認即可 |
| **C** | Major Revision Required | 任一必須項未通過，或 > 3 項建議缺失 | 作者修正後重新送審 |

**判定規則**：必須項未通過自動判 C；可選項缺失不影響等級。

**審查紀錄格式**：

```markdown
| 審查項 | 結果 | 備註 |
|--------|:----:|------|
| {檢核項} | ✓ / ✗ | {修正說明} |

**審查結果**：{A / B / C}
**審查者**：{姓名} / {日期}
```

### 4.4 安全分級

PXA 報告 **必須** 依三級分類：

| 等級 | 定義 | 發行範圍 |
|------|------|----------|
| **公開** | 不含敏感資訊，可公開發行 | 無限制 |
| **內部** | 含公司內部技術資訊 | 專案團隊＋組織內部（含授權承包商） |
| **限制** | 含出口管制、智慧財產或客戶機密資訊 | 具名授權人員，須經核准權責主管核准 |

### 4.5 文件發行授權（DAA）

DAA 為 PXA 報告的發行管控機制，參照 NASA NF-1676 精神與 AR 70–31 資訊保護原則，裁剪為民間組織簡化版。DAA **必須** 包含五區段（表單模板見 SP-002 §7）：

| 區段 | 內容 | 填寫時機 | 負責人 |
|------|------|----------|--------|
| **§I 文件識別** | 標題、編號、作者、版本、日期、專案 | 產出時自動填入 | 撰寫者 |
| **§II 分類與發行** | 安全等級、出口管制、發行範圍、智慧財產 | 作者審閱後 | 文件作者 |
| **§III 作者聲明** | 確認內容分類正確性 | 作者審閱後 | 文件作者 |
| **§IV 審查與核准** | 技術審查 → 管理審查 → 核准權責主管核准 | 審查流程 | 審查鏈 |
| **§V 處置** | 存檔、發送、公開 | 核准後 | 文管人員 |

### 4.6 出口管制

涉及出口管制技術之報告，**必須** 於封面、書名頁、DAA §II 標示管制類別。PXA 工程師 **建議** 諮詢法務確認是否涉及 ITAR/EAR 或我國相關出口管制法規。

## 5. 證據與來源品質

品質標記共兩套系統＋一個行文旗標，各回答一個問題：

| 系統 | 標記 | 回答的問題 | 定義 |
|------|------|-----------|:----:|
| 文獻層級 | L1 / L2 / L3 | 引用來源的權威程度？ | §5.1 |
| 信度 | ★★★ / ★★ / ★ / ⚠ | 這個數值/結論有多可靠？ | §5.2 |
| 佐證旗標 | ✓ / ⚠ | 這個論點有沒有交叉確認？（行文旗標，併入 ★ 判定） | §5.2 |

> 原 E1–E4 證據等級系統已廢除（v3.0）——其資訊已由 ★ 判定條件涵蓋。

### 5.1 文獻層級

引用文獻 **必須** 標註文獻層級：

| 層級 | 定義 | 範例 |
|------|------|------|
| **L1** | 專案內文件（可完整追溯） | PXA 技術報告、專案規格文件 |
| **L2** | 教科書、同行審查文獻，或經機構技術審查之正式出版品 | Raymer、Roskam、AIAA Journal；NASA TM/TP/CR（裁定：一律 L2） |
| **L3** | 補充參考（非同行審查） | 技術手冊、供應商數據、線上資源、課程講義（如 Okawa、MIT OCW） |

### 5.2 信度與佐證

**佐證旗標**（行文中，驗證比較用）：`✓`＝≥ 2 個獨立來源或方法交叉確認；`⚠`＝單一來源或缺佐證（**必須** 說明風險，缺口列入 TBD 清單）。

**信度判定樹**（依序檢查，符合第一個條件即停止）：

| 條件 | 信度 |
|------|:----:|
| IF 實測數據 AND 多來源交叉驗證（✓） | ★★★ |
| IF 實測數據 AND 無交叉驗證（⚠） | ★★ |
| IF 教科書理論 AND 案例驗證（✓） | ★★ |
| IF 教科書理論 AND 無案例驗證 | ★ |
| IF 單一文獻 OR 工程估算 | ★ |
| IF 假設值 OR 待驗證 | ⚠ |

**vault status 對映**（以 vault 為證據來源者適用）：

| vault status | 意義 | 佐證旗標 | [C-n] 信度上限 |
|--------------|------|:----:|:----:|
| `stable` | 內容經逐式對照 PDF 原文核驗 | ✓ | ★★（★★★ 仍須實測＋多來源） |
| `reviewed` | 結構驗證通過、內容未逐式核驗 | ⚠ | ★ |
| 筆記內含 ⚠ 標註 | 原刊存疑或無法核驗 | ⚠＋沿用存疑說明 | ⚠ |

### 5.3 狀態標記

| 標記 | 意義 | 使用情境 |
|:----:|------|----------|
| PASS | 滿足約束，裕度 ≥ 10% | 合規矩陣 |
| WARN | 滿足約束，裕度 < 10% | 合規矩陣 |
| FAIL | 不滿足約束 | 合規矩陣 |
| TBD | To Be Determined（數值不存在，待決定） | 待決清單 |
| TBC | To Be Confirmed（數值存在，待確認） | 待決清單 |

**狀態燈判定**（摘要或結論使用狀態燈時）：達成且裕度 ≥ 10% → 🟢；達成但裕度 < 10%、有附加條件、TBD 待驗證、或未達成但有緩解方案 → 🟡；未達成且無緩解方案 → 🔴。

**風險等級判定**（風險登錄，SP-002 §5.6）：L × C（各 1–5）：1–4 低；5–9 中；10–25 高。

### 5.4 可追溯性與假設管理

| 規則 | 說明 | 判定 |
|------|------|:----:|
| 參數追溯 | 每個參數 **必須** 標註來源（上游階段/文獻/供應商/計算） | [H] |
| 決策追溯 | 每個設計決策 **必須** 標註理由與替代方案 | [H] |
| 需求追溯 | 每個需求 **必須** 可追溯至上游來源與下游驗證 | [H] |
| 假設管理 | 每個假設 **必須** 標註類型（✓ 已驗證 / TBC 待驗證 / Design 設計假設）與驗證狀態 | [H] |

### 5.5 證據鏈

技術報告之證據來源有二，可擇一或並用；所用來源 **必須** 於緒論或書名頁背面說明：

| 證據來源 | 追溯鏈 | 適用 |
|----------|--------|------|
| **obsidian vault** | 報告 → 原子筆記 → source note → PDF 頁碼 | 專案內有經 QA gate 驗證之知識庫時優先使用（結構驗證 `check_vault.py`＋內容抽驗回對 PDF 原文） |
| **專案證據文件** | 報告 → 專案文件（模組規格文件、規格書、論文原檔、測試資料）之章節 → 原始檔頁碼或資料檔 | 無 vault 之專案；依專案資料夾編排規則找出證據文件 |

| 規則 | 說明 | 判定 |
|------|------|:----:|
| 追溯鏈 | 每個技術陳述 **必須** 可沿上表之追溯鏈找回原文或原始資料 | [H] |
| status 分級 | vault 筆記：`draft`（初稿）→ `reviewed`（結構驗證通過）→ `stable`（逐式核驗通過）；對映見 §5.2。專案證據文件無 status，佐證旗標依 §5.2 逐項判定 | — |
| SSoT 迴寫 | 撰寫中發現證據來源（vault 或專案文件）有誤 **必須** 先修來源再寫報告，**禁止** 只在報告端修正；無權修改之來源則於報告明列差異 | [H] |
| L2 協調制 | 研究性質報告之文獻回顧 L2 ≥ 5 為**建議**目標而非硬性門檻：數量緊繃時 **必須** 回報使用者裁量，**禁止** 沉默帶過 | [S]（計數回報） |
| 不得以記憶充當證據 | 找不到證據來源時 **必須** 停下詢問，**禁止** 改用記憶或自行假設資料位置 | [H] |

## 6. 數值規範

| 規則 | 說明 |
|------|------|
| 有效位數預設 | 3 位有效數字（除非 Profile 另有規定） |
| 單位制 | SI 制為主；航空慣用單位（ft, kts, lb）**可選** 並列 |
| 常數 | 專案通用常數定義於 Profile（如 g, ρ₀, ν₀），正文 **禁止** 自行定義不一致的值 |
| 無因次量 | 2–3 位有效數字 |
| 百分比 | 2 位有效數字 |

學科特定數值規範 **必須** 定義於專案 Profile，本標準不重複定義。

## 7. 取捨研究格式

當存在多個候選方案時，**必須** 使用以下格式：

```markdown
#### 方案選擇：{主題名稱}

**問題陳述**：{一句話說明需要決定什麼}

**評估標準**：
| 標準 | 權重 | 理由 |
|------|:----:|------|

**候選方案**：
| 方案 | 優點 | 缺點 | 適用情境 |
|------|------|------|----------|

**評分矩陣**：
| 方案 | 標準1 | 標準2 | 標準3 | 加權總分 |
|------|:-----:|:-----:|:-----:|:--------:|

**選定方案**：{方案名稱}
**選定理由**：{2–3 句量化支撐}
**放棄方案**：{方案及原因}
**重新評估條件**：{觸發條件}
```

| 規則 | 說明 |
|------|------|
| 候選方案 | **必須** ≥ 2 個 |
| 評估標準 | **必須** ≥ 3 個，權重總和 = 100% |
| 選定理由 | **必須** 量化支撐（句型：「選定 X，因其在 Y 指標上優於 Z 達 N%」） |
| 重新評估 | **必須** 定義觸發條件 |

## 8. 術語定義

| 術語 | 定義 |
|------|------|
| **SP** | Special Publication；本體系僅指 SP（標準） |
| **TR** | Technical Report，技術報告（研究、設計、測試） |
| **TP 骨架** | 對標 NASA Technical Publication 之內文架構（SP-002 §3.0）；為結構名稱，非報告類別 |
| **報告性質** | 研究／設計／測試，決定必要章節（SP-002 §3.1） |
| **TM／TP（舊制）** | 合併前之報告類型，僅存在於已編號之報告（§2.5） |
| **DAA** | Document Availability Authorization，文件發行授權 |
| **STRN** | Standard Technical Report Number，標準技術報告編號 |
| **vault** | obsidian 知識庫——經 QA gate 驗證之證據來源（§5.5） |
| **前頁 / 本文 / 後頁** | Z39.18 三段式結構（SP-002 §2） |

專案特定術語 **必須** 定義於對應之 PXA-PROF-{專案}，不於本標準中定義。

## 9. 修訂與發佈紀律

1. 任何規則變更 **必須** 落在 STD 正本（版本遞增＋版本紀錄行，依 §3.7），**禁止** 只改 SKILL.md 或下游 skill。
2. 修訂後同步：pxa-standards SKILL.md 之裁定表與版本表、前頁工具版本表（SP-002 §7）、scribe skill 之章節引用。
3. 新裁定流程：先記入 `documents/SP-series-map.md` 裁定紀錄（即時生效）→ 修訂對應 STD 文件 → 同步。
4. [S] 規則之新增/變更 **必須** 同步修訂 `check_sp.py`——腳本與條文不一致時以條文為準並立即修腳本。
5. 修訂涉及上位標準解讀時，**必須** 回查 skill `raw/` 原文，不憑記憶。
6. 歷史版本與退役文件存 `documents/reference/archive/`。
