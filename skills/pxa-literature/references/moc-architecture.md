# MOC 架構參考 — 兩層式知識庫組織（自 25kg eVTOL 結構佈局知識庫實戰萃取）

> 本檔為 SKILL.md §階段一-5 的深化參考：當主題規模大（原子筆記 ≳20 則、或天然涵蓋多個子領域）時，
> 單一 MOC 會撐爆——索引變長列表、綜合層失焦、缺口混在一起。此時改用**兩層式架構**。
> 範式來源：「基於空氣動力條件的結構佈局規劃」知識庫（總覽＋6 領域、55 篇文獻、120+ 筆記），
> 經使用者實戰驗證產出品質高，故固化為慣例。
> 本檔給規格（What）；**實例與寫法（How it reads）見 `example-MOC-golden.md`**——動筆前兩份都讀。

## 一、兩層架構

```
總覽 MOC（1 份）                     領域子 MOC（每領域 1 份）
├─ 設計情境（具體參數表）             ├─ 領域定位（在工作流中的位置＋對應 RQ/SP）
├─ 研究框架（RQ 沿用編號）            ├─ 核心概念（依理論脈絡分節，僅本領域）
├─ 領域導覽表（含就緒度）             ├─ 理論脈絡／推導鏈（領域內部依賴）
├─ 全域理論脈絡（跨域推導鏈）          ├─ 方法比較矩陣（含「本情境適用性」欄）
├─ 全域 SOTA（逐 RQ 一句話）          ├─ SOTA 評述（把握程度分層誠實陳述）
├─ 跨域缺口（交 scout）              ├─ 待釐清／缺口（scout-ready 語句＋⟳ 追蹤）
├─ SP Roadmap（依就緒度排序）         └─ 對應交付（SP）
└─ 文獻來源總表（全 sources）
```

分工原則：**總覽管「跨」、子 MOC 管「深」**。細部索引、比較矩陣、領域缺口住子 MOC；
總覽只留導覽表、跨域推導鏈、逐 RQ 一句話 SOTA 與跨域缺口——兩層不重複內容。
文獻來源總表住總覽（E3 覆蓋檢查的錨點）；子 MOC 只列本領域相關者。

## 二、領域切分邏輯（預設骨架）

依「工程問題的自然階層」切分，而非依文獻堆的形狀切分：

| 序 | 領域類型 | 例（結構佈局案） | 通用意涵 |
|----|---------|----------------|---------|
| ① | **邊界條件／輸入** | 設計基準與載重 | 問題的上游：規格、載荷、環境、法規 |
| ② | **核心方法／建模** | 結構建模與關鍵參數 | 把問題化為可分析模型與判準的中樞 |
| ③ | **材料／實作介質** | 材料與製造 | 方法落地的物理載體與製程約束 |
| ④⑤ | **應用域**（可多個） | 機翼佈局／機身佈局 | 方法在各具體對象上的應用 |
| ⑥ | **進階／參考層** | 進階方法與參考 | 「有能力時深化、非初步必需」的降級收納 |

切分準則：每個領域對應**至少一條 RQ 與一份交付（SP）**；領域間依賴畫成單向鏈
（上游 → 下游），與 SP 信任鏈一致。新主題不必湊滿六個——按此邏輯裁剪，
但「邊界條件在前、進階參考殿後」的次序保留。

## 三、品質機制（兩層都適用，這些才是範式的靈魂）

1. **設計情境錨定**：總覽開頭放一張具體參數表（載具/速度/Re/結構型式…），
   且**每份子 MOC 頂部重複一行設計情境**。作用：所有萃取、比較、SOTA 判斷都對著
   「這個設計」下結論，而不是泛泛的文獻綜述——這是知識庫品質的第一驅動力。
2. **誠實就緒度**：總覽導覽表逐領域標「就緒度（高/中/低）＋一句原因」；缺口重的領域
   在子 MOC 頂部用 callout 明講（如「本領域為知識庫最大缺口」），並誠實區分
   「可借用的通用原理」與「主題專屬但 vault 未涵蓋」。寧可標低，不可虛胖。
3. **比較矩陣加「本情境適用性」欄**：通用欄（假設/適用/驗證層級/成本）之外，
   **必加一欄**逐法回答「對本設計情境的適用性與限定」（如「低 Re 下適用性佳但保守」
   「多不適用（金屬一體加工），惟理念可借鏡」）。這一欄是矩陣從文獻摘要變成工程判斷的關鍵。
4. **降級標記，不刪除**：對本情境非驅動的方法（如低速下的 flutter）明確標
   「監控／驗證層」「選配」「參考層」並給理由——保留知識、降低其在決策中的權重，
   而不是假裝它不存在或讓它虛佔核心位置。
5. **缺口追蹤（⟳）**：待釐清條目寫成 scout-ready 缺口語句；缺口被部分補齊時**不刪原條目**，
   在其下加 `⟳ 部分已補（YYYY-MM，補了什麼）：…；仍缺…`——缺口的收斂歷程可追溯，
   且「仍缺」半句讓下一輪 scout 有精確目標。
6. **增補紀錄**：後續併入的筆記/文獻在「核心概念」與「文獻來源」加註
   `（增補 YYYY-MM 併入）`小節或行內標記，讓知識庫的成長層次可見。
7. **拉式交付對應**：每份子 MOC 末尾標對應 SP；總覽的 SP Roadmap **依就緒度排序**
   （就緒度高的先寫），而非依領域編號——知識生產由交付需求拉動。

## 四、QA 對應

- 兩層皆為 `type: MOC`；子 MOC frontmatter 加 `subtopic:` 欄。
- 總覽以 wikilink 串接全部子 MOC；E3（MOC 覆蓋率）以「總覽＋子 MOC 聯集」計。
- check_vault 對 MOC 的章節檢查：總覽須含「研究框架」＋「待釐清」；
  子 MOC 須含「領域定位」＋「待釐清」（腳本已支援二擇一）。
